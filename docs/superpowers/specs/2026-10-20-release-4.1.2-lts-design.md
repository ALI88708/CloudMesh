# CloudMesh 4.1.2 LTS Release Design

Status: approved after independent builder check
Author: assistant
Date: 2026-10-20
Supersedes: `audit/4.0.1-stability`

## Purpose

Cut `4.1.2` as the first CloudMesh LTS release: a version a customer can run
for months without chasing feature updates, while still receiving planned
security fixes.

The user's versioning rule is:

- `4.1.x` adds security features.
- `4.1.2` is the stabilization release that fixes known problems.

The practical target is **12 months of support**, with no feature backports to
the `4.1.x` line. "No errors" is not a measurable promise; the release target
is **no known critical or high-severity defects, a green verification suite,
and a documented residual-risk list**.

## Baseline and release shape

The repository's real published baseline is `3.4.0` (`main`, tag `v3.4.0`).
`4.0.0` exists only on `audit/4.0.1-stability`; it was never tagged or
published. This changes the release path:

- `4.1.2` is the first published 4.x artifact.
- The upgrade path under test is **3.4.0 -> 4.1.2**, including the JSON-to-SQLite
  migration and the plaintext-to-encrypted profile migration.
- `4.0.0` remains the internal BSD/hardening checkpoint recorded in the
  changelog.
- Rollback means **reinstall the 3.4.0 wheel and restore the pre-upgrade
  backup**. There is no in-place data downgrade.

Delivery uses one release branch cut from `audit/4.0.1-stability`:

1. Create `release/4.1.2` with all unpushed 4.0.0/4.1.x work.
2. Implement and verify the release there.
3. Merge the release branch into `main`, then tag `v4.1.2` on the merge commit.
4. Publish the GitHub release. No `v4.0.0` tag is created.

## Release channel

CloudMesh is **GitHub-release-only**. The `cloudmesh` name on PyPI belongs to a
different project, so the current `pip install cloudmesh` and
`pip install --upgrade cloudmesh` instructions are a supply-chain hazard.

The release therefore includes:

- README, CONTRIBUTING and site install instructions that use a GitHub release
  wheel or a source checkout, never the bare PyPI name.
- A rewritten `cm update --pip` that downloads the matching wheel and
  `SHA256SUMS` from the GitHub release, verifies the digest, and installs the
  local wheel.
- `cm update --git` retained for developers, with a warning that it tracks
  `main` and is not the LTS channel.
- LTS patches published as GitHub releases in the `4.1.x` line. Features are
  not backported.

## Version plan

| Version | Role |
| --- | --- |
| `4.1.0` | Security-feature baseline for the 4.1 line. Changelog checkpoint. |
| `4.1.1` | Fixes found while validating 4.1.0. Changelog checkpoint. |
| `4.1.2` | Supported LTS artifact; the only version published and tagged. |
| `4.2.x` | Next feature line. Features are not backported into 4.1.x. |

`4.1.0` and `4.1.1` are explicitly marked in the changelog as internal
checkpoints, not published releases. This satisfies the project's changelog
history rule without shipping an intermediate artifact.

## Supported platforms

- **Python 3.11, 3.12 and 3.13.** Python 3.10 reaches end of life in October
  2026, so promising it for a 12-month LTS would promise security patches for
  an unsupported interpreter. `requires-python` becomes `>=3.11`; the CI matrix
  and classifiers change with it.
- Controller: Windows, Linux, FreeBSD, OpenBSD and NetBSD.
- Node agent: Linux and the BSD family; the controller remains the Windows
  target.
- The REST API is **loopback-only**. Remote access is through an SSH tunnel;
  4.1.2 does not add cleartext external binding or API TLS.

## Goals

1. Close every open item in `docs/AUDIT.md` or record it as accepted risk.
2. Add a bounded set of security features that materially improve the default
   posture.
3. Prove stability with repeatable soak, restore, upgrade, and failure tests,
   not only unit tests.
4. Make the release auditable: version consistency, changelog, checksums, SBOM,
   dependency audit, support policy, and release notes.
5. Leave the repository ready to cut `4.2.0` without carrying release debt.

## Non-goals

- Promising zero defects or independent certification.
- General feature work, UI redesign, or website expansion.
- A Windows node agent.
- Changing the MIT license or the CLI-first product shape.
- Backporting features into `4.1.x` after release.
- A new node wire protocol. The shared-key/TLS/SPA model stays as-is; its
  limitations are documented.

## Security scope

### 1. API hardening

- `/api/exec` is opt-in with `--enable-exec`; the default API is read-only.
- An optional `--allow-command` list permits only exact command strings when
  exec is enabled. The existing dangerous-command blocklist remains defence in
  depth, not a sandbox.
- The API binds to `127.0.0.1` only. There is no external-bind flag in 4.1.2.
- The API key is generated per run and printed once at startup, or supplied by
  `--api-key-file` for automation. CloudMesh never persists a generated key.
  On POSIX, a supplied key file must be mode `0600`; Windows relies on the
  per-user profile ACL and is documented as such.
- Add `X-Content-Type-Options: nosniff`, `Cache-Control: no-store`, and
  `X-Frame-Options: DENY` to every API response, including errors.
- Authentication failures are logged to the process log, rate-limited per IP.
  They are **never** appended to the command ledger; an unauthenticated client
  must not be able to evict real command history.
- Authenticated API exec calls are recorded in the command ledger as
  `api:exec` events.

### 2. Update-channel safety

- `cm update --pip` installs only a GitHub release wheel whose SHA-256 matches
  the release's `SHA256SUMS`.
- No code path invokes `pip install --upgrade cloudmesh` against PyPI.
- Install/update documentation names the GitHub release URL explicitly and
  warns that the PyPI `cloudmesh` name is a different project.

### 3. Remote temporary-file safety

- Replace fixed `/tmp/.cm_my.conf` and `/tmp/.cm_pgpass` paths with `mktemp`
  files, `umask 077`, and a shell cleanup trap.
- Never fall back to a predictable path when `mktemp` fails.
- Add tests for cleanup on success and failure.

### 4. Command-ledger rotation

The ledger currently keeps 500 entries and rewrites the file on every command.
After entry 501, `cm cmdlog --verify` reports a broken chain because the first
retained entry points at a dropped entry.

- Store a checkpoint containing the hash of the last dropped entry.
- Verify from the checkpoint, so trimming does not look like tampering.
- Handle legacy truncated logs without a checkpoint by anchoring at the first
  retained entry and reporting that the earlier history is unavailable.
- Keep the existing `clear` behavior, removing the checkpoint too.

This closes a real tamper-detection bug and lets authenticated API exec events
use the ledger safely.

### 5. Secrets and permissions

- `cm doctor` checks `.secret.key`, `config.json`, `.node_keys.json`, the
  SQLite database, and `data/acl.json` for group/world readability on POSIX.
- Add a remediation hint; do not silently chmod user files.
- Keep profile encryption and legacy plaintext migration behavior.
- Node auth failures are recorded in the **node's** log. The controller cannot
  distinguish a wrong key from an unreachable or malformed node without a
  protocol change, which is out of scope; this limitation is documented.

### 6. Release integrity

- Build wheel and sdist in CI.
- Publish SHA-256 checksums with the release artifacts.
- Generate a CycloneDX SBOM for the release environment.
- Attach GitHub build-provenance attestations.
- Keep the existing `pip-audit` hard gate.
- Keep the existing release-notes extraction gate.

### 7. Audit visibility

- Authenticated API exec calls go to the command ledger.
- API authentication failures go to the process log, rate-limited per IP.
- Panic/key-rotation events stay in `.panic_log.json`.
- Node authentication failures stay in `cloudmesh_node.log`.
- No new competing audit store is introduced.

## Stability scope

### Verification layers

- Existing suite: all tests green on Windows and Linux.
- BSD workflow: existing VM suite plus the new hardening tests.
- New unit tests for every security behavior.
- New integration tests for API lifecycle, backup/restore, and upgrade.
- A repeatable one-hour soak gate: monitoring, reconnect, API, ledger, and
  storage operations against a disposable local environment.
- An optional 72-hour soak run for the release owner, using the same harness
  and recorded in the release checklist. It is not a CI job.
- Fault injection: dropped SSH connections, malformed node responses, locked
  database, wrong key, and interrupted restore.

### Release gates

- Zero known P0/P1 defects. P0/P1 are defined in `docs/LTS.md`.
- Full suite green; skipped-test count explained in the release notes.
- `pip-audit` reports no known vulnerabilities in the release environment.
- Backup/restore drill passes.
- Upgrade from `3.4.0` to `4.1.2` and rollback-by-reinstall pass in a sandbox.
- API default behavior is documented and tested.
- Version is consistent across `pyproject.toml`, README, site, changelog, and
  `test_release_metadata.py`.
- Tagged artifact installs in a clean virtual environment and passes the CLI
  smoke test.
- One-hour soak passes; 72-hour result is recorded or explicitly waived.

## Deliverables

- `pyproject.toml` version `4.1.2`, `requires-python >=3.11`.
- `CHANGELOG.md` sections for `4.1.0`, `4.1.1`, and `4.1.2`.
- `SECURITY.md` supported-version table and LTS policy.
- `docs/LTS.md` support window, P0/P1 definitions, patch rules, and EOL policy.
- `docs/UPGRADING.md` for `3.4.0` to `4.1.2`.
- `docs/AUDIT.md` updated with closed and accepted findings.
- Release badge and test-count badge updated.
- `v4.1.2` tag and GitHub release with checksums, SBOM, and attestations.
- One `release/4.1.2` branch merged to `main`; no direct push to `main`.
- No `v4.0.0` tag; 4.0.0 remains the internal changelog checkpoint.

## Decisions taken

- Support window: **12 months** from the `4.1.2` release date.
- Only `4.1.2` is published and tagged.
- API exec is **disabled by default**; this is a deliberate breaking change
  documented in the upgrade guide.
- The API stays loopback-only; remote exposure is unsupported.
- Generated API keys are per-run and never persisted.
- Python 3.10 is dropped; 3.11-3.13 are supported.
- `docker exec` remains an operator-supplied command surface. It is accepted
  risk, not a defect: the command is the feature, and the container is the
  trust boundary. The audit note is reclassified accordingly.
- Security patch releases inside `4.1.x` are allowed for critical/high issues;
  feature releases are not.

## Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| `--enable-exec` breaks existing scripts | Upgrade guide, clear 403 message, release-note callout. |
| Dropping Python 3.10 blocks a user | Upgrade guide; 3.10 is EOL; install docs state 3.11+. |
| `mktemp` differs across Linux/BSD | POSIX template and BSD VM test. |
| Command-ledger checkpoint is tampered with | It is local tamper evidence, not notarization; checkpoint and log are both mode `0600`, and truncation is reported. |
| `cm update` cannot reach GitHub | Clear error; source-checkout path remains; no silent PyPI fallback. |
| One-hour soak misses a slow leak | Optional 72-hour run is documented and recorded before public announcement. |
| LTS promise outlives maintainer capacity | 12-month window, security-only scope, published EOL date. |

## Approval gate

Approved on 2026-10-20 with these user decisions: one `v4.1.2` tag, no separate
`v4.0.0` release, Python 3.10 dropped, and long verification split across
parallel subagents. The first implementation slice is release scaffolding and
version consistency; security changes follow in separate commits so each can be
reverted independently.
